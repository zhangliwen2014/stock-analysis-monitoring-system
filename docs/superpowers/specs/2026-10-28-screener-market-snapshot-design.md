# SP3 选股：全市场快照 + 多条件组合 + 筛选方案维护

**Goal:** 让「筛选股票」在屏幕上真的可用：一个市场几千只票里按多条件组合（例：A 股
`PR < 0.5`）筛出一篮，条件能保存、能改名、能改内容、能删除，命中的票能勾选或一键加进自选。

**Architecture:** 选股今天只有命令行一条腿（`sams screen pr` → `services/screen.py`），而它的票池是
「库里 `financials` 表有行的代码」——那个数与一个市场的几千只差着三个数量级，所以做成页面第一件事
不是画界面，是**换票池的来源**。这一期加一条横截面能力（一次调用拿全市场那一天的快照，落库留按日历史），
在其上立一张**字段注册表**（每个可筛字段自带来源、单位口径、可用市场、可否为空），条件引擎与页面都只读
这张表。加字段 = 注册表加一行：页面下拉、校验、覆盖率报告同时跟上，没有第二处要改。

**Tech Stack:** akshare（A/HK/US 板块快照）+ 既有 `AdapterRegistry`/`CAPABILITIES` 契约、Polars、
DuckDB（两张新表）、FastAPI + Jinja + htmx（CSP `'self'`，条件构建器是服务端渲染的表单）。

## 1. 用户的原话（需求现场）

1. 「没有看到筛选股票的页面，比如查看 A股中 PR < 0.5 的股票，筛选股票应该支持多个条件组合」
2. 「选股功能是投资很重要的一环」
3. 「选股的筛选条件 记录，可以保存/修改/删除等维护」

**架构按长期的三类数据（估值 / 基本面 / 价格行为）一次设计对，数据分两步接**。

## 3. 决策

- **D172 选股页的第一块砖是票池，不是页面。** 沿用 `synced_codes` 做票池的页面，今天打开会写
  「范围：A 股 3 只」，那一句会让人以为这系统在选股上没用。所以本期先接横截面快照，
  页面与引擎在它有数之后立刻接上（同一次交付，但顺序不可颠倒）。
- **D173 新增一条能力 `market_snapshot`，与逐票能力分家。** 现有 `CAPABILITIES` 的每一项都是
  「一只票的一次取数」，按 `(market, code)` 路由；快照是「一个市场的一次取数」，返回几千行。
  它不进 `_walk` 那套按票的重试（一次失败就是整市场失败，重试同一个 URL 没有意义），
  但**进 `CAPABILITIES` 表**，因为「这个市场有没有快照」与「这条链有没有源」是同一个问题，
  答案必须来自同一处（D165 立的那条规矩）。
- **D174 票池 = 当日快照 ∩ 该市场代码表，且页面第一行永远先报范围。** 快照里有代码表里没有的票
  （退市整理、新上市未进表）与表里有快照里没有的票（停牌当日不给行），两个数都单独报，
  不合并成一个「有效票池 N 只」了事——那正是 `services/screen.py` 那段 docstring 防的假话。
- **D175 快照落库并留按日历史；页面只读库。** 一次采集几千行、几十列，落库的成本远低于每开一次页面
  打一次外网；而留历史才可能有 `52 周位置`、`上周命中那批现在怎样`这类问题。
  `snapshot_daily` 主键 `(market, day, code)`，另存 `taken_at`（当天那次采集的时刻）。
- **D176 采集时机 = 每日盘后自动一次 + 页面一个「立即重采」按钮（只排队）。**
  「进页面现采」不做默认：同一天的同一组条件两次点进去必须给同一篮票，否则页面上那句话
  （「今天 A 股便宜的一只都没有」）没法追溯。「盘中反复采」只是同一个 job 的 cadence，
  不需要现在为它承担 5000 行 × 每天几十次的写量与限速冲突（架构不变，将来一行配置的事）。
- **D177 现值 PR 是一个**新字段**，不是把 `pr` 换个来源。** 快照给 `PE(动)` 与 `PB`，
  于是可以按恒等式 `ROE = PB ÷ PE` 推出当期 ROE，代进 D59 那条 PE 支：
  `PR_现值 = PE(动)² ÷ (100 × PB)`。它与年报 ROE 那条是两个口径、两个数（前者随价变，
  后者随披露变），所以：注册表里是两条字段（`pr` 与 `pr_now`），各带自己的 `basis`，
  **永不同篮排序、永不在同一个比较里混用**；页面上选中哪一条，范围行就跟着写哪一条的口径名。
  `ROE_implied ≥ 1` 沿用 `out_of_caliber` 那条拒算，不另写一份。
- **D178 条件是 `(字段, 比较符, 值)` 的列表，v1 只允许 AND。** 加 OR 的代价不是表达式解析，
  而是覆盖率报告要从「每条条件各算一遍」变成「每个子句各算一遍」——那是第二轮的账，
  现在预付没有意义。比较符 `>= > <= < =` 与 `between`；`between` 的两个数写反了就 400 说清，
  不自动交换（D58 那一类「静默替调用方改写请求」的错法）。
- **D179 一张字段注册表是唯一的条件词表。** 每一项声明：列来源（哪张表哪一列，或哪个表达式）、
  单位（比值小数还是百分数——D58 就栽在「0.4 还是 40」）、可用市场、可否为空、是否分篮、
  显示名与一行解释。页面下拉、参数校验、覆盖率、结果表列头全部由它生成。
  **新增字段只改这一处**；写第二处的 PR 就是把「屏幕上能选但服务端不认」做出来。
- **D180 每一条条件必须报三个数：通过 / 不通过 / 无数。** 「无数」单独计数并在页面上点名，
  且当它占比过半时那一屏顶部出警告。理由与 `screen.py` 的 `NO_ANNUAL_ROE` 同一条：
  `PR ≤ 0.5` 最想找的是困境反转与周期底部，而那类票恰恰最容易算不出数；
  静默丢掉它们，结果看起来完整，实则把这条规则最该抓的东西筛掉了（D43/D60）。
- **D181 结果里的每一行带它被筛出来时那一份数，不是最新数。** 快照是 `day` 那天的；
  行上再打一次实时报价会让人对着一张「昨天的 PR」做「今天要不要买」的决定，
  而页面上没有任何一处说清这两者差了一天。范围行写死那一个 `day`，行上不再给别的时点。
- **D182 筛选方案（条件记录）是 per-user 的一张表，支持完整的增删改查。**
  `screener_presets(id, user_id, name, market, conditions_json, created_at, updated_at)`。
  用户要的是「保存 / 修改 / 删除等维护」，落地成六个动作，缺一不可（见 §7.3）：
  保存、重命名、改条件（覆盖原记录）、删除、复制一份、直接重跑。
  **覆盖而不是插新行**：一个人改自己的「便宜 + 有质量」时，预期是那一行变掉，
  不是多出一行不知道哪个是新的；`updated_at` 就是那条记录「什么时候是现在这样」的证据。
- **D183 方案与 `scan_results` 各管一件事，不合并。** 前者是「人想 repeats 的一句话」，
  后者是「某天扫出来的那一篮」（D57 的既有姿势：子集扫描故意不落库）。
  跑一个方案时照旧写 `scan_results`（`strategy_id` 用方案名 + 条件哈希），于是
  「上周那个方案命中了哪 12 只、这周还剩几只」有地方可查，而方案表里不会长出日期。
- **D184 加自选走既有那条路，批量也要经它。** 单行「加自选」、勾选多行「加自选」、
  一键「全部 N 只」三种入口，最后都调同一个 `watchlist` 写入点，
  且都先给一句 dry-run 数（「全部 N 只里有 M 只已经在自选里，实际加入 K 只」）。
  「全部」这一条**越过分页**：一屏只列 50 行，但用户点的是那一篮，不是那一屏——
  所以它必须在服务端重跑条件，而不是把页面上那 50 行提交回来。
- **D185 快照列名漂移要出声。** 横截面接口是这套系统里最容易被上游改列名的一类调用
  （几千行 wide payload，没人逐字看）。解析层照 `FieldDrift` 的姿势：缺关键列就抛，
  让采集 job 失败并写告警，**绝不**把缺的列读成 null——那等于全市场该列无一例外变成「无数」，
  而屏幕上写的是「这一条没票通过」。

### 3.1 开工前的实测修正（2026-10-28）

设计写完就量了源。四条实测把 §4 的源、签名、字段与市场范围改掉了：

- **D186 快照的源换成腾讯批量报价，东财三个 `*_spot_em` 在本机全不通。** 实测：
  `ak.stock_zh_a_spot_em` / `stock_hk_spot_em` / `stock_us_spot_em` 一律
  `ConnectionError: RemoteDisconnected`，`curl https://push2.eastmoney.com/api/qt/clist/get`
  连 curl 都回 000。而仓库里已有现成通道：`tencent.QUOTE_URL` 的批量报价是 GBK 的
  JS 赋值语句（`quote_get` 早就按 GBK 解码），实测一条请求能带 **880 个代码**
  （URL 7941 字符），**1000 个回 414**（URL 9021 字符）。于是 `spot.py` 走腾讯，
  `SPOT_BATCH = 800`：全 A 5577 只七批、每批约 0.4 秒。
  字段位置是按四只票（茅台、平安银行、腾讯、苹果）交叉核对过的：A 股 1 名称、
  3 现价、30 时间、32 涨跌幅、35 复合「价/量/额」、38 换手、39 PE(TTM)、43 振幅、
  44 流通市值、45 总市值、46 PB、49 量比、52 PE(动)；全在 A 股这一种行里。
- **D187 能力签名是 `market_snapshot(market, codes)`，票池由服务层给。** 适配器不读库
  （与全仓「适配器只认代码」一致）；服务层从 `symbol_master` 取活跃代码——「这个市场
  有哪些票」仍然只有一个出处。源答不出的代码由服务层点名，不静默过滤。
- **D188 本期快照只供 A 股。** 腾讯港股行的 PE/PB 位置与 A 股不同，且无法交叉验证
  （47 位在四只票上是 1.37/4.34/1.00/6.94，与 PB、派息率都对不上；58/65/72 三个候选
  也逐个对不上已知财报）；美股行更短，46 位是英文名。拿不准的口径不注册：
  `SpotAdapter.spot_markets = frozenset({"A"})`，HK/US 在注册表那层写「不供」，
  页面置灰与 note 共用它。要港美股，先补一次与年报交叉核对的实测。
- **D189 快照列去掉 `chg_60d / chg_ytd / listed_hint`（本期）。** 那几格（62/63/64/65/66/
  74/75）的实测值找不到可交叉验证的语义；把猜出来的列写进库，等于给「60 日涨跌」
  这个条件一个假数。需要就日后拿日线自算。
- **D190 现值 PR 的有效区三件事：`PE(动) > 0`、`PB > 0`、推出来的 ROE 不过口径上界。**
  亏损票 PE 为负、平方后变正，`PE² ÷ (100×PB)` 会给出一个「便宜」的假数；PB 为负
  （资不抵债）同理。任一条不成立时 `pr_now` 记空并在「无数」里点名，原因分句
  （亏损 / 净资产为负 / ROE 推出超过 |1|），口径闸仍走 D59 的 `out_of_caliber`。
- **D191 v1 词表 = 快照列 + `pr_now` + 三只财务列（`roe`/`revenue_yoy`/`profit_yoy`）。**
  年报口径的 `pr`（`ScreenService.pr_max` 那条）**不进**词表：它自带两支公式与一套
  PIT 闸门，进通用引擎等于写第二份 PR 实现，而财务票池今天只有 3 只——没有数据能把它
  跑对。注册表已预留 `basket` 字段，将来加它时用同一条校验拦混选（D59）。
- **实测票池：`symbol_master` 里 A 股 5577 只活跃**（含北交所 `920xxx` 353 只，

## 4. 数据层

```
能力：market_snapshot(market, codes) -> 该市场当日的横截面（只含 codes 里源答得出的）
落点：TencentAdapter.market_snapshot（D192）
纯函数：src/sams/datasource/spot.py —— 字段位置表、A 股 symbol 前缀、解析器、空帧、探针
        源：https://qt.gtimg.cn/q（GBK，quote_get 已解码）
        每批 SPOT_BATCH=800 个代码（实测 880 可、1000 回 414）
意愿表：TencentAdapter.market_snapshot_markets = frozenset({"A"})（D188）
落库：  0023_market_snapshot.sql → snapshot_daily(market, day, taken_at, code, name,
        price, pct_chg, amount, turnover_rate, volume_ratio, amplitude,
        pe_ttm, pe_dyn, pb, market_cap, float_cap, is_st, source)
        主键 (market, day, code)；一列对应一个源列，映射表只写在 spot.py 一处；
        day = 这一批报价里最多的那个交易日期（停牌票的旧时刻不改写这一天）
调度：  不进逐票的 `_DATA_JOBS`（那条是按票池 fan-out 的），单列市场级 `spot` job；
        手动补采 `sams sync spot` 与自动跑同一条服务函数，只是 caller 不同
```

字段随数据到齐才能筛：快照列先落，注册表里那些「来源是财务表」的字段（`roe`、`revenue_yoy`、
精确 `pr`）在票池同步铺起来之前会大面积报「无数」——**它们照样出现在下拉里**（D165：
档留在原位、点了仍回一句为什么），因为「词表里有但这一市场没数」与「词表里根本没有」
是两件不同的事，前者是数据进度，后者是功能缺失。

## 5. 引擎

```python
# src/sams/services/screener.py
@dataclass(frozen=True)
class Condition:
    field: str      # 必须是注册表里的名字
    op: str         # ">= > <= < = between"
    value: float | tuple[float, float]

def run(market, conditions, *, day=None, limit=None) -> ScreenResult
```

`ScreenResult` 从范围开始，逐条可追溯：

```
market, day, taken_at, universe_size, market_size,
fields: 每条条件的 {passed, failed, missing, caliber}   # D180 的三个数
hits:   每行是 {code, name, 该条件用到的那几个字段值, pr_basis}
excluded_missing: 无数出局的票，带原因与下一步命令（沿用 screen.py 的词表）
truncated: 命中超过 limit 时给出「还有 N 只未列」，不让一屏假装是全部
```

两条 PR 同选时直接 400（不是「按其中一条排序」，也不是分篮混排）——D59 那条判断在页面上
比在命令行更容易被误犯，所以由服务端拦。

## 6. 页面 `/screen`

1. **范围行（顶部，永远第一行）**：`A 股 · 快照 2026-10-28 15:05 · 票池 5123 只（代码表 5180，快照缺 57）`
   + 「立即重采」+ 快照超过 N 天时的一句提醒。
2. **条件区**：一行一个条件（字段下拉 / 比较符 / 值 / 删掉这一行），「再加一条」与「删一条」都是
   服务端往返（CSP 禁内联脚本，没有前端加减行的脚本）。字段下拉按注册表生成；
   当前市场没数的字段**置灰但仍列出**，`title` 里是那句为什么（复用计划 B 刚落地的 `class="dim"` 姿势）。
   单位在字段名后面写清（`市赚率 PR（小数比值，0.5 = 0.5 不是 50%）`）——D58。
3. **结果区**：表格，列头就是这几条条件用到的字段加名称/代码；每行一个「加自选」（已自选的标出来，
   点了不重复插）；表头上方「勾选的加自选」与「全部 N 只加自选」，后者先给 dry-run 数（D184）。
4. **方案区**：已存方案的列表与六个动作，见 §7.3。

页面尺寸与提交姿势（不留到实现时再定）：结果一页 **50 行**，`PAGE_SIZE+1` 判下一页；
条件区是一次 GET（可收藏、可刷新），加减行是服务端拼好的链接；整张结果表只是一个
`<form>`，行内「加自选」与「勾选加」「全部加」是同一表单里 value 不同的提交按钮
（CSP 禁内联脚本，也不为了按钮去引一段前端状态机）。加自选后 303 回同一组条件，
结果由服务端按 URL 重跑——与「全部」越过分页的姿势是同一条。

## 7. 存储与方案维护（D182 的落地）

### 7.1 迁移

- `0023_market_snapshot.sql` — `snapshot_daily`（2026-10-28 实测时 `storage/migrations/`
  最大是 0022，计划 C 尚未跑，所以计划 D 取 0023；计划 E 顺位 0024）。
- `0024_screener_presets.sql` — `screener_presets`（计划 E）。
- 计划 C（每用户图表偏好）晚于计划 E 时取 0025；编号以实际执行时的最大值为准，
  **不用「预留」占位**（占位会在两个计划并行时撞号）。

### 7.2 表结构

```sql
screener_presets(
  id VARCHAR PRIMARY KEY,          -- uuid4 的 hex：与全仓其他表同一种主键（DuckDB 没有自增列）
  user_id VARCHAR NOT NULL REFERENCES users(id),
  name VARCHAR NOT NULL,
  market VARCHAR NOT NULL,
  conditions_json VARCHAR NOT NULL, -- [{field, op, value}, ...]，条件为空不允许存（见 7.3）
  created_at TIMESTAMPTZ NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL,
  UNIQUE (user_id, name)
)
```

`(user_id, name)` 唯一：两个人各有一个「便宜」互不干扰，同一个人存两个「便宜」则必须自己选
改名还是覆盖——服务端不能替他猜哪个是要的那个。

### 7.3 六个动作

| 动作 | 端点 | 语义与要说清的边界 |
| --- | --- | --- |
| 保存 | `POST /screen/presets` | 存当前条件 + 市场。空条件不许存（那是一条永远为真的筛法，重跑时看起来像「方案坏了」）。同名同用户：给一句「已有同名方案，覆盖还是改名」，不静默覆盖也不静默加 `(2)`。 |
| 列表 | `GET /screen`（同页） | 按 `updated_at` 倒序，每行显示名字、市场、条件的可读摘要（不是 JSON），与「上次跑」的时间（取 `scan_results` 里这个方案当前 `strategy_id` 的最近一条 `created_at`；没跑过写「没跑过」）。 |
| 重跑 | `POST /screen/presets/{id}/run` | 按存下的条件跑**今天**的快照——存的是条件不是结果，所以 PR 口径变了或数据缺了要在结果顶部说出来，而不是默默给一个不同的篮子。重跑同时写 `scan_results`（`strategy_id = screen:<名字>:<条件哈希前 8 位>`，D183）。 |
| 改名 | `POST /screen/presets/{id}/rename` | 撞名同样出声。 |
| 改条件（覆盖） | `POST /screen/presets/{id}` | 覆盖 `conditions_json` 与 `updated_at`；名字不动。 |
| 删除 | `POST /screen/presets/{id}/delete` | 只删那一行方案。**不动 `scan_results`**：那天的那一篮是发生过的事实，方案没了它照样可查（D183）。已加进自选的票更不会因为删方案而消失——「我删了筛选条件，昨天加进来的票还在」是这个功能唯一的正确行为。 |

六个端点全部要求登录，`user_id` 从会话取，路径里的 id 不属于当前用户一律 404（与个股页
「不给探测者区分『没有』与『不是你的』」同姿势）。

### 7.4 一处口径

方案的 `conditions_json` 里存**字段名与数值**，不存显示文案：字段在注册表里改名或换单位时，
老方案要能被重新解释并**在结果顶部说明它现在算的是什么**。因此注册表项带一个 `caliber` 短码，
方案里存短码 + 值；短码不再存在时不猜，直接说「这一条用的字段已不在词表里，请改方案」。

## 8. 错误处理

- 快照一天都没有：页面 200，范围行给「这个市场还没有快照，下一步 `sams sync spot --market A`」，
  条件区整块不渲染（渲染了也是点一个 400）。
- 采集失败：保留上一次那天的数据 + 顶部一句为什么与重采命令；**绝不**渲染成「这个市场没有便宜票」。
- 条件写错（字段不认识、值不是数、市场不支持该字段、两条 PR 混选）：`ValidationError` → 400，
  说清可选的是哪些（与指标名、视图名同一姿势）。
- 库被调度线程握着：`DatabaseLocked` → 503（全局处理器已有），页面不自己拼状态码。

## 9. 测试钉（行为，不是实现步骤）

1. 票池 = 快照 ∩ 代码表，且两个缺口分别报数（`snapshot_only` / `list_only`）。
2. 每条条件三个数：passed / failed / missing，三者相加 = 票池大小——这一条是最便宜的防「静默丢票」。
3. `PR ≤ 0.5` 含等号；`0.5` 是小数口径（写 `50` 不会被认为是 50%）。
4. `pr` 与 `pr_now` 同时出现 → 400，两篮不混排（D59/D177）。
5. 注册表每一项都被页面下拉与校验器认到：加一行字段，两处同时亮——用一条「遍历注册表」的参数化测试钉住，
   防止词表长成两份。
6. 快照缺关键列 → `FieldDrift`，不是那一列全 null。
7. 方案 CRUD 六动作各一条，加三条边界：同名不许静默覆盖、空条件不许存、别人的 id 给 404。
8. 删除方案不动 `scan_results`、不动自选。
9. 「全部 N 只加自选」在服务端重跑条件，越过分页；已在自选的不重复插，且报出「实际加入 K 只」。
10. 范围行在任何结果之前出现在 HTML 里（这一条钉的是文案顺序，不是数字）。
11. live 标记一条真接口冒烟：A 股快照确实拿得到几千行且关键列齐（这条默认在全量之外，
    验收时单独跑并点头）。
12. 批大小是常量：800 个代码一条请求，改到 1000 就是全市场 414（实测边界 880/1000）。
13. 北交所 `920xxx` 用 `bj` 前缀；用公共的 `a_share_symbol` 会发成 `sz`、静默缺 353 只。
14. `pr_now` 在 `PE(动) ≤ 0`、`PB ≤ 0`、推出来的 ROE `|x| ≥ 1` 上是「无数」，不参与比较
    （负 PE 平方后会把亏损票筛成「便宜」）。
15. 快照响应按 GBK 解码；按 utf-8 读会在第 14 个字节崩在首行票名上。

## 10. 拆成两个计划

- **计划 D「全市场快照 + 选股引擎」**：`market_snapshot` 能力与适配器、`snapshot_daily`（迁移）、
