# 数据完整性与「凡输入标的处给候选」（设计）

起因是两条用户反馈：

1. 「自选股、持仓股每天资料会自动更新吗？比如美团，加入自选很多天了，连 K 线都没有，
   其他股票也有不少信息都不全。」
2. 「每个输入股票的地方，都应该可以通过代码 / 拼音首字母 / 股票名称等带出股票列表，
   所有地方都检查一遍。」

这一份把两条各自追到底：第一条不是「没同步」，而是**同一个 bug 的两个下游**（源的一次
正常空答复被读成接口改版 → 公司行为确认写不下去 → 复权闸把库里已有的 K 线一起挡掉）；
第二条是**同一个入口重复造了十次，只造对了三次**。

## 0. 现状事实（2026-11-01 从 `data/sams.duckdb` 的一份拷贝里数出来的）

采集链本身在跑，且覆盖面是对的：夜里的清单是「自选 ∪ 持仓 ∪ 启用规则目标 ∪ 在跟论点」
的并集（`services/scheduler/universe.py`），用户停用不过滤采集。`bars` job 近三天
`A 504/504`、`HK 3/3`、`US 1/1`，全部 `ok`。所以「没更新」不是调度漏了谁，是**更新回来了
但读模型拒绝出数**，或**源答成「没有」**。

| 事实 | 数 |
| --- | --- |
| HK 03690（美团）在 `bars_daily` 里的日线 | **85 根**（2026-07-02 ~ 10-30） |
| `corp_actions_coverage` 里 HK 的行 | **1 行**（只有 00700） |
| `corp_actions` 里 HK 的行 | 26 行 / 1 只票 |
| `valuation_daily` 覆盖的市场 | 只有 A（503 只） |
| 自选里 **0 根日线** 的活跃代码 | 24 只（23 只北交所 920xxx + 000996） |
| `akshare_hk` 连败次数 | 134（`FieldDrift: 港股分红响应缺少必需列 ['除净日','分红方案']，实际列 []`） |
| `yfinance` 连败次数 | 1737（`Too Many Requests`）， valuation/actions 两条链都被它卡住 |

美团那条链是通的：`GET /api/symbol/HK/03690/bars` 回 `dates: []`，note 是复权闸的原话
——「`corp_actions` 里 0 行既可能是这只票从没分过红，也可能是没查过它」。而库里那 85 根
就是被这句话挡掉的。

**根因（已实测）**：`ak.stock_hk_dividend_payout_em("03690")` 回的是 **0 行、7 列齐全**
（从没派息在港股是常态），而 `akshare_hk_payout` 把 `len(frame) == 0` 折成
`pl.DataFrame()`——**列丢了**。`expand_payout` 第一件事就是 `required_columns`，
于是「源答了没有」被读成「源改版」，抛 `FieldDrift`。后果是三层：这只票每晚失败一次、
公司行为确认永远写不下去、复权闸永远拒绝它已有的 K 线。

对照：`yfinance` 那条链早就写对了——`corp_actions` 里显式留了一句「一只从不派息的票是
真实存在的状态，给它一次成功的空答复，覆盖标记（D36）才写得下去」。港股这一路少了这层
照顾，而服务层（`services/corp_actions.py`）其实完全接得住空答复：`confirmed_empty_by`
会为每个答「没有」的源各记一行覆盖。**缺的只有那 7 个列名。**

## 2. 已修：港股「从没派息」是一次答复，不是一次故障（D269）

`akshare_hk_payout` 只在 `frame is None` 时回无列空帧；0 行照原样交给 polars，列留住。
形状判据由 `required_columns` 继续守着——**它守的是「有没有答」，不是「有没有内容」**，
这一点写进注释，否则下一个人会把两处一起「优化」掉。

钉住的测试：`tests/datasource/test_hk_actions.py::test_a_zero_row_payout_response_keeps_its_columns`
（把 2026-11-01 实测到的那 7 个列名写死成 `LIVE_COLUMNS`，接口再改版时会以断言失败的形式
出声，而不是变成 134 次静默失败）。

**这一修能让美团的图回来吗？不能，只让它离回来近一步**：港股公司行为链上还有
`yfinance`，而它正在被限流。 registry 的判据是「链上每个有能力的源都独立答了『没有』」
才写确认（`fetch_actions`：`if empties and not unanswered`），只要 yfinance 挂着，
akshare_hk 一个人的「没有」就不能写成覆盖。这条判据本身是对的（替一个没答上来的源确认
= 替它说谎），要动的是 §4。

## 3. 已做：候选面板一份、共用监听一条（D270）

现状是同一个入口被写了四遍：`watchlist.html`（加入自选）、`portfolio.html` 的成交录入
（`scope=fills` + 一段页面内联 JS）、`base.html` 的导航搜索（`scope=nav`）、
`partials/quotes.html` 报价板上那张「加入自选」的隐藏表单。
而另七处只有裸输入框：

| 位置 | 字段 | 要的形态 |
| --- | --- | --- |
| `rule_form.html` 对象引用 | `target_ref` | `A/600519` |
| `rules.html` 示例规则 | `code` + 市场下拉 | 两格一起写 |
| `theses.html` 建论 | `code` + 市场下拉 | 两格一起写 |
| `portfolio.html` 限额对象 | `scope` | 裸代码 |
| `news.html` 关键词只盯一只 | `code`（市场是隐藏域） | 裸代码 + 换市场 |
| `news.html` 筛选 | `q` | **名称**（标题里出现的是名字，代码搜不到） |
| `admin_sources.html` 探源 | `code` + 市场下拉 | 两格一起写 |

做法：新增 `pick` 面板（`partials/pick_candidates.html`），一行同时带上
`data-pick-market` / `data-pick-code` / `data-pick-ref` / `data-pick-name`；`app.js`
加一条 document 级委派监听，**写进「这个 form 里真存在的那几格」**。
不为每个字段名开一个面板——那等于把同一份表格抄七遍，而第七遍之后没人再对齐过。

**面板种类在 URL 路径上，不在查询参数上（D274）**：`/api/symbol-search`（加入自选）、
`/api/symbol-search/nav`、`/api/symbol-search/fills`、`/api/symbol-search/pick`。
这条是 2026-11-01 真浏览器量出来的（`tmp/_cdp_pick.mjs`，走 Chrome 9222）：htmx 发的
请求体是「**这个输入框自己的值（用它的 name）+ `hx-include` + `hx-vals`**」，它**不**自动带
整张表单（成交那格正是靠 `hx-include` 才带上市场，量出来才有 `market=A`）。原来那版把种类
做成 `?scope=pick`，靠 `hx-vals='{"scope": "pick"}'` 盖进去，而限额那张表单的对象格**恰好叫
`scope`**——同名时 `hx-vals` 赢，发出去的是 `?scope=pick`，用户敲的那串字一个字都没进请求，
面板永远空着，页面看起来却接好了线。种类进了路径，就没有任何字段名能与它相撞；先试过的
「把检索词抄进隐藏 `term`」那条路是走不通的（htmx 连隐藏域也不会自动带），已经删掉。

于是**检索词只有一条来路：格子自己的 name**。端点认识的名字与「什么算一个标的入口」的
判据必须是同一份，所以 `TERM_FIELDS = ("code", "q", "target_ref", "scope")` 放在
`dashboard.py`，模板守卫测试直接导入它当扫模板的名单——新增一页表单时名字没进这份，
那一页就出不了候选，测试会说不通的是模板而不是让屏上静默空着。

三条约束值得钉住，都写在监听与模板注释里：

* 市场格（下拉或隐藏域）跟着所选行走。资讯关键词那张表单里，市场是隐藏域；
  选了 HK 的票却把市场留在 A，落库的是一条永远匹配不上的关键词。
* 代码类字段只写非隐藏的 `input`。`<input type="hidden" name="code">` 带的是这一屏
  已经在用的过滤条件，替用户改掉它是悄悄换了查询。
* 候选容器 id 必须以 `-candidates` 结尾（监听靠它收起面板），且**pick 那几张**容器都在
  自己的 `<form>` 内（监听靠 `closest("form")` 定位字段）。自选页的 `#wl-candidates` 在
  表单外是允许的：它走默认面板，那一行的「加入」是一张真 POST 表单，不靠这条监听。

钉住的测试：
`tests/web/test_symbol_inputs_have_candidates.py` 扫模板而不是点页面——这条要求的失败方式
正是「以后新加一张表单时没人回头接线」。它按 `<input name∈TERM_FIELDS>` 找入口，排除隐藏域
与候选面板自己，要求每个入口带 `hx-get="/api/symbol-search…"`、一个真实存在的
`hx-target="#…-candidates"`、**不带 `hx-vals`**（带了就会吃检索词），并且 `hx-get` 的路径段
必须是端点认识的种类。第三测试反过来钉判据本身（自选页那个必须被扫到、候选面板自己不许被
算成入口），否则前几条会退化到对着候选面板提要求而集体通过。

实机量到的九个格子（2026-11-02，`tmp/_cdp_pick.mjs` + `tmp/_cdp_click.mjs`）全部出候选并
全部能「填入」：`/watchlist`、导航搜索、`/rules` 示例、`/rules/new?kind=price.cross_below`、
`/theses`、`/portfolio` 限额、`/portfolio` 成交、`/news` 筛选、`/news` 关键词。
`/admin/sources` 探源那一格只过了静态判据——验收账号 `sp1check` 不是管理员，那个页面 403，
不为量一格而改任何人的角色。

## 4. 提案：覆盖确认不下来时，图画裸价并明写未复权（D271，待确认）

现在「拒绝出数」同时管着两件事：数字（区间收益、指标、决策卡、归因）和图。
数字进决策，谎不得——没有覆盖确认就不能把裸价涨跌说成复权涨跌，这条判据不动。
但图给人看的是走势形状，**一句「未确认除权记录，此为裸价，跨除权日会跳」就够了**：
它把「我们没查到」和「这只票跌了 40%」分开说，用户看到的是诚实的降级而不是一片空白。
今天的情况恰好相反：屏幕上是空白，用户只能猜是数据没有、票没上市、还是系统坏了。

要动的只有出图那一路（`/api/symbol/{market}/{code}/bars` 与 `chart.html` 的图注），
读模型其余消费者保持 `NotAdjustable`。判据从「有没有覆盖」变成「这句话谁在听」。

**风险说在前面**：裸价图上跨除权日的那一跳会被读成暴跌。所以这条降级只在图注里写明，
且不给均线/指标叠加（那些是要进决策的数）。不做也可以——那就必须接受「美团这类票在页面上
等于没有行情」。

## 5. 已修：北交所按沪市问、又按沪深端点问，24 只「所有源都说没有」而 job 报 504/504 ok（D272）

原因是交易所号段判错，而不是窗口太宽。北交所（43 / 83 / 87 / 88 / 92 号段）必须带着
`bj` 去问：东财的 `secid` 是 `0.`、F10 的代码是 `BJ920020`。我们按**首位**判交易所
（`569` → 沪），于是 `920020` 被发成沪市。三家源各自的答复正好凑成一句谎：

- 东财对问错交易所的代码回 `data: null`，解析层把它读成 `EmptyResponse`——一句「这只票从来没交易过」；
- 腾讯 `sh920020` / 新浪 `sz920020` 回空行（`param=bj920020` 才有行）。

链上每一格都答「没有」，`_fetch_bars_frame` 于是收敛成 `empty_everywhere`，
`sync_daily` 走 `logger.info` + `written=0`。**这在 job 的 note 里与「今天追平了」长得一模一样**：
`_collect` 只在抛 `SamsError` 时记失败，所以那句 note 是「504/504 只日线」，
而其中 24 只页面上连一根 K 线都没有——用户问的「美团为什么没有 K 线」就是这么来的。

三处改动，各钉一枚测试：

1. **号段只写一处**。`core/codes.py` 新增 `BEIJING_PREFIXES` / `is_beijing(code)`，
   `datasource/base.py:a_share_symbol` 先分流北交所再按首位分沪深；东财的数字编号
   （`secid`）、F10 的后缀（`f10_code`）、资金流标签（`fund_flow_market`）、腾讯快照
   （`spot_symbol`）、腾讯端点（`kline_path`）全部从这一格推，删掉原本散在四个适配器里的
   三份复制判据。按**两位**判而不是按首位：`92` 与沪市 B 股 `900` 首位相同，一位判据会把
   北交所问成沪市，而 `900901` 仍必须是 `sh900901`（测试里钉住这两条）。
2. **腾讯那条端点也不认 `bj`**（号段修完才看得见）。`fqkline/get` 对 `bj920020` 只回
   `day` 数组里的**最后一根**，同一串参数在 `newfqkline/get` 上回 245 根（实测 2026-11-02）。
   这一层比第一层阴：它不是空答复，是一条字段齐全、日期正常的单根序列——入库一行、
   `mark_done_by_code` 把补数队列结掉、`run_bars` 记一次成功，而图上只有一个点。
   `kline_path(market, symbol)` 只把北交所换端点：沪深与港美照旧（新端点对它们给的行更宽，
   能越过问出去的 `start` 往前多要几百根，收不收那些行是另一个问题，不在这一片顺手改）。
3. **note 必须说出不完整**。`run_bars` 把「今晚没写进任何行**且**库里仍没有一根日线」的
   票单列计数：`504/504 只日线，24 只一根 K 线都没有`。
   为什么不用「所有源均无数据」当判据：那个条件每个交易日会把几十只**当天停牌**的票
   一起念进来，而几十句噪音的下场是没人再读这一句——库里已有日线的不算窟窿。
   哪几只不在 note 里列：空答复不 `mark_done_by_code`，第二天仍留在 `symbol_backfills`
   队列里，三次之后转 `deferred`——点名与积压那一头已经有了（§0 那张表），缺的只是

实测验收（改后）：`TencentAdapter.daily_bars("A", "920020", 2024-11-01, 2026-11-02)` 回
**245 根（2025-10-28 起）**、`920976` 回 736 根（2023-10-18 起，那只票的北交所历史更长），

**实机复查（2026-11-02，`serve` 在跑，从库的只读副本查）**：自选里的北交所票 **31 只全部有

## 7. 已修：上一进程留下的 `running` 行，在新进程认领心跳时一次结掉（D275）

问「资料每天自动更新吗」的时候，`sams health` 里有 **26 行 `status=running`**：它们属于
早就被杀掉的进程，却把「最近一次」的位子占着，健康页于是把一次死掉的运行念成「正在进行」。
模块注释里那条「六小时才算崩溃」（D105）原本管的是**一轮常驻循环之内**的并发读，
被误读成「孤儿行可以留三天」。

改在唯一说得清的那一刻：DuckDB 是单写者，新进程能认领心跳就等于**没有别人在写库**，
那么库里挂着的 `running` 只能是上一个进程被杀留下的。`TaskRunRepo.close_interrupted()`
一次把它们结为 `failed`，`error` 写「上一进程未收尾：本进程启动时结为失败」——这句话要
自己站得住，因为 `sams health` 只打印 `error` 的前 60 个字符。接线在 `run_forever` 里
`_claim()` 之后、进循环之前，并打一行 INFO 说结了几行。

## 8. 已修：三百秒内的重启不再把夜里那一趟关掉（D276）

这是「资料没自动更新」更直接的解释。`run_forever` 原本撞在 `SchedulerBusy` 上就退出：
上一个进程刚刚打过的拍还新鲜（`HEARTBEAT_STALE_S = 300`），于是**每次重启只要落在 300 秒
以内，这个进程整个生命周期都没有调度器**——页面照常、日志安静、夜里的 job 不再跑。
2026-11-01 我自己就这么踩了一次（重启后 `serve.log` 里只有一句 `SchedulerBusy`）。

接管要的证据我们恰好有：单写者模型下，只有真没人持锁才可能有第二份写连接，所以
**库旁那个拍（D111）里写下的 pid 若已不存在，「上一个 owner 死了」就是可靠结论**。
`_owner_is_gone()` 用 `os.kill(pid, 0)` 判：`ProcessLookupError` 才算证据，
`PermissionError`（在，但不是我的）与读不到文件、拍的 `beat_at` 比库里那行旧，都**不算**；
只有算得出来才把那一行 `stop()` 掉再接管，并 WARNING 写明接管了哪一份库。
判不动的时候维持原样（`SchedulerBusy`）——把「不确定」说成「可以抢」比多等三百秒危险得多。

## 10. 已修：健康读数分清「进程停了」与「某一趟 job 比阈值长」（D278）

`/healthz` 报 `degraded`、`sams health` 报「常驻调度器可能已经停了」，而那个进程正在老实清扫
基本面：`_beat()` 只在轮首与每个 job 之前打，**单个 job 之内没有第二个线程**（这条边界
`heartbeat.py` 一直写明着），于是任何一趟超过 `HEARTBEAT_STALE_S = 300` 秒的采集都必然带上
一段「过期但其实活着」。误报的代价不是难看，是把习惯教坏：那一晚每次刷新都亮 ⚠，
读的人从此不看这一屏。

分得开靠的是一件已经在库里的东西：`task_runs` 里那行 `running`。但它能不能当活证据，
**取决于读它的是谁**——这是这一片真正的难点：

* **同进程的读者**（`/healthz`、管理员健康页）：写这行的就是握着库的这个进程，所以
  `ScheduleData.running` 是硬证据。新增 `busy`（「有，且还没老到崩溃证据」）与
  `may_be_stopped = stale and not busy`，两者都从 `collect` 算出；屏幕上说的是
  「心跳已经 6 分钟没更新，但正在跑「financials」（A，已 5 分钟）：这一趟之内不补拍」，
  `status` 留在 `ok`。
* **进程外的读者**（`sams health`）：它**能打开库**这件事本身就说明没有进程握着锁
  （DuckDB 单写者，连只读连接都会被拒，D111），那几行 `running` 只能是上一个进程留下的
  孤儿（D275）。所以这里继续按 `stale` 下结论、退出码照旧是 1，只把孤儿点出来
  （「库里还挂着没收尾的执行：「actions」已 5 分钟…下一次启动会结掉它们」）——
  那一句回答的是「为什么这一晚一个 job 都没跑」。把上面那句照抄到这里，等于把一次
  已经死掉的运行说成还在做活，而读退出码的人收到「一切正常」。

「还没老到」用的是 runner 那条现成的六小时（`STALE_RUNNING_H`，D105）：不做这道区分，
一行死数据就能永久供着「它还在跑」。

`pid_is_gone()`（同一个切片里加的）是同一件事的第三读者：库被握着时外部读者连库都打不开，
`sams health` 只能读库旁那个文件，于是那里按「那个 pid 在不在」分三句印——明确不在（「锁不会
自己释放，这一份库现在没人写」）、还在（「多半是某一趟采集比阈值长」）、判不出来（两句都不许说）。
D276 的接管逻辑也改问这一个函数，`os.kill` 不再有两份各自的解释。

钉住的测试：`tests/services/test_scheduler_service.py` 的「过期 + 有还新鲜的 running ⇒
`may_be_stopped` 是 `False`」与「那行 running 已经七小时 ⇒ 仍是崩溃证据」；
`tests/storage/test_task_runs.py::test_running_names_the_rows…` 钉查询本身；
`tests/cli/test_health_cli.py::test_a_stale_beat_names_the_hanging_rows_without_trusting_them_as_life`
钉「进程外的读者不许把孤儿当活证据」（退出码仍是 1）；
`tests/services/test_runtime.py::test_a_long_job_running_now_does_not_degrade_the_status`
与 `tests/web/test_admin_web.py` 那两枚钉同进程那一路。

实机：重启 `serve` 后 `/healthz` 立刻给出 `{"stale": false, "busy": true, "running": [{"job":
"actions", "market": "A", "age_s": 5}]}`；`sams health` 在库被握着时仍是退出码 3 那一屏
（「心跳 30 秒前 · PID …（常驻循环还在写）」）。

## 11. 撤掉：「下单那道入口不校验代码形态」（D280 核过，不是缺口）

`sim_positions` 里有一只 `(A, 01021)`，qty 0、`open_ts` 为 NULL，而 `sim_orders` 里关于
`01021` 只剩一笔 `HK` 的买入。这两条拼起来说的是同一件事：有人**按 A 市下过一笔
`01021`**，之后撤销成交——`ledger.record_fill` / 撤销那条路（`ledger.py:688`）会把
`INSERT OR REPLACE` 写进 `sim_positions`，撤销时把订单行删掉、把 0 股的持仓行**留在库里当历史**。
于是那只从没成立过的市场键永久留下了。

本节原本点名的两条「漏的」，**读代码后都不成立**（原话留在这里，是为了下次不再从现象倒推缺口）：

1. ~~入口不校验~~ —— 校验有，而且只挂在一个格子上。`sim_orders` 全库只有**一个**写入口
   （`record_fill`，`ledger.py:589`），两道闸就在它前面：`_check_code_shape`
   （`ledger.py:390`：A 必须 6 位、HK 归一后 5 位、US 不猜）与 `_check_market_of_code`

   `services/portfolio.py`、CLI 三条路都汇进这一个入口，所以「表单里搜不到判据」不等于
   「没有判据」——放在会被绕过的地方才算漏。测试早就钉住了：
   `test_a_five_digit_code_in_the_a_market_points_at_hk_connect`（拒的同时
   `_order_rows == 0`，不留半个痕迹）、`test_the_master_sees_a_hk_code_recorded_as_a_share`
   （主档有货时先被 D206 那句拦下，形态闸是主档空着时的第二道保险）。
   那只 `(A, 01021)` 是这两道闸**装上之前**留下的历史行。
2. ~~撤销该把零股行收干净~~ —— 那是已定的口径，不是 bug。§5.4 决定「0 股行是历史不是持仓」，

## 12. 已修：连败到阈值的源先放一边（D279）

夜里那几趟 job 慢，有一大截不是采集得多，是**同一堵墙被反复撞**。这一句只对「链上有第二个门
可敲」的那几条成立，单源那几条要的是另一件事——见本节末尾的实测覆盖表。`source_health`（2026-11-02 读库）：
`yfinance` 连败 **1784** 次、`akshare_ths` **1176** 次、`eastmoney` **881** 次——都是几小时前的
事，而且早就定性了（`Too Many Requests` / `No tables found` / `RemoteDisconnected`）。
降级链不知道「定性」这件事：`_walk` 每只票都要把链上每个有能力的源真调一遍，
一个源一次判定就是 `attempts_per_source = 3` 个请求加 1、4 秒退避。`task_runs` 里对应的数
（2026-11-02 00:00–04:18 这几趟，读库）：`financials A` 一趟 **26.6–46.0 分钟**、
`flow A` **13.6–35.5 分钟**，而这两趟里真正拿到行的只有 494/505 只。

改法只有一句：**这个源已经连败 10 次了，接下来半小时别再叫它**。

1. `registry` 加两个常量与一个进程内的 `cooling_until`：`COOLDOWN_AFTER_FAILURES = 10`
   （为什么是 10：一次判定已经是 3 个请求，10 次 = 30 个请求 + 半分钟的退避，
   足够说清「它今天就是不答」；再往上加只是继续烧预算。计数是**连续**的、任何一次成功
   都清零，所以一个六成成功的源要连撞 10 次才冷却——那本来就不是「偶尔抖一下」的形状）、
   `COOLDOWN_S = 1800`（够短，一个夜里醒来好几趟，源恢复不用等到下一班 job）。
2. `_walk` 在调用之前问一次 `_cooling(name)`，在冷却里就产出一条 `failed` 结果：
   `tries=0`（D27：只报真实调用次数）、错误话写「冷却中，还有 N 秒」、
   `cause` 是 `TransientError`——于是全链失败时终端错误仍是「下轮再试」，
   job 不会把它升成一句永久的失败。复用 `failed` 这一格而不是新造第四种 `kind`，
   是因为六条消费链对「这个源这次没答上」的归类完全一致，新增一格只会让 D36 那句
   「谁没答上来就不能签确认」要各写一遍。
3. 链走完那句话跟着分堆（D65 的延长）：`_failure_note` 按 `tries` 把失败源拆成
   「真调用过又失败的」与「本次未调用的」两堆打印。不拆的话 serve.log 里会出现
   「真调用过又失败的 akshare: 429」这句我们没做过的事，而下一个人会据此再撞 10 次
   去确认一件已经定性的事。能力缺失那一堆（`被跳过的源`）照旧独立，三句话三种下一步。
4. 冷却里的跳过**不是一次新的失败**（不 `_mark_failure`）：把它计进去，一晚上连败数会冲到四位数，
   而那句「连续失败 N 次」再也说不出它真试过几次。
5. **链上只剩一个有能力的源时不冷却**（实测有哪几条是这种形状，见本节末尾那张表：
   US 的公司行为、三个市场的财务与估值、A 的资金流）。冷却它们等于整晚「什么都答不上来」，
   而那个空会被下游读成「这只票没分过红」「这只票没有估值」（D36 那一侧）。
   冷却是止损，不是自造不可用。
6. 到期不等于恢复：`_cooling` 顺手清掉标记，**下一次真实调用就是探针**（半开）。探针再失败
   就重新冷却半小时，所以一晚上最多撞它 24 次而不是 500 次；探针成功则 `_mark_ok` 清空。
7. 不持久化。`source_health` 那行照旧只有 `consecutive_failures` / `last_error`，
   冷却跟着进程走——但**连败计数本来就落库**，所以重启后第一次失败就把冷却重新挂上，
   付得起的代价只有一轮探针。为它加一列、加一条迁移，只会把一个止损机制变成
   一份要维护的持久状态。也因此**不把「冷却中」显示给另一个进程**——
   `sams health` 里的冷却标记说的会是「一个没在跑的进程」，那是句假话。

不进冷却的三条链是刻意的：`fetch_fx` / `fetch_symbol_list` / `fetch_market_snapshot`
每趟 job 只调一次，不是 500× 的放大，给它们加闸门只会在真正需要汇率或快照时少一个源。

**实机（2026-11-02 04:24，重启 `serve` 后）**：重启时库里带着 `akshare_ths` 连败 1176 的计数，
第一次失败就把冷却挂上了（正是第 7 条说的那一轮探针）：

```
2026-11-02 04:24:58 WARNING sams.datasource.registry: 源 akshare_ths 冷却 1800 秒
（连续失败 1177 次），这期间链上直接换下一个源
```

那句话在一个进程里只出现**一次**，不是每只票一次；挂上之后 `source_health` 里它的连败数
停在 1177 没再涨（04:37 读库），本进程的 `sams.retry` 里一次 `akshare_ths` 都没有。
`yfinance` 在 04:44:12 同样挂上冷却（连败 1785），而它之后仍被调用了几次（1786–1790）——
那几次全部落在 `valuation US/HK`，也就是第 5 条说的孤源链，行为与设计一致。
